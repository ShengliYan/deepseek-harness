# Agent Note: Chat scroll-to-top auto paging

Status: implemented

[English](2026-08-16-chat-scroll-to-top-auto-paging.md) | 中文

## Problem

更早的聊天历史只能通过消息流顶部居中的「加载更早」按钮获取：读者必须先停在顶部、对准控件、点击一次，上一页才会加载。这一手势打断了回读流程（向上滚、点一下、再向上滚），而且按钮是获取更早历史的唯一途径——当已加载窗口比视口还短、根本没有可向上滚动的顶边时，仍然被迫去点按钮。

## Decision

到达顶部即翻页手势。`ChatView` 中，读者滚动到达最顶部（scrollTop ≤ 2 px，且经 observed-top 台账判定为读者输入）时，沿按钮曾经使用的同一锚定路径拉取更早的一页：将第一个可见的已定稿行登记为翻页锚点，调用 `loadOlder()`，到达的 prepend 再把该行恢复到原视口位置。点击入口被移除；页面在途期间，原地渲染一个不可交互的「加载中…」小胶囊。

三条支撑路径保证没有按钮时每个位置仍然可达：

- **补满（Fill）：** 每次布局遍历中，已加载窗口短于滚动视口（`scrollHeight - clientHeight < 1`，且 `clientHeight > 0`，使零度量的 jsdom 保持惰性）时自动翻页，直到消息流产生溢出——否则短尾页没有顶边，更早历史将无法到达。
- **恢复到顶：** 重挂载时保存的阅读位置恰落在顶部，无法再通过过度滚动获得滚动事件（位置无法移动），因此在仍有历史时自行翻页。
- **链式 prepend：** 一页太短、恢复后的位置仍停在顶部边缘时，直接翻下一页，而不是把读者晾在那里。

空闲时清除锚点改为按状态迁移判定：锚点在 `loadingOlder` 完成 true→false 迁移时清除，而不是只要标志为 false 就清除——因为触发翻页的那次滚动同时改变了底部归属，可能在会话的忙碌标志进入快照之前就提交了一次渲染。重入不是组件要管的事：`Session.loadOlder` 会去重并发请求，且无 `hasMore` 时直接空转。

## Alternatives considered

**保留按钮，只加滚动触发。** 否决：按钮会沦为死掉的外壳——到达顶部时页面在读者能点击之前就已加载，而点击唯一还能派上用场的场景（短而不溢出的窗口）已由补满路径覆盖。

**用更深的阈值（提前几百像素预取）。** 否决：按接近程度预取会加载读者并未索取的页面（一次甩过顶部边界的 fling 就会触发），而且触发必须保持读者输入归属，台账只为真实移动提供这一保证。

**只移除按钮、不加补满。** 否决：短于视口的尾页无法滚动，更早历史将完全不可达——那是按钮最后一项职责。

## Consequences

回溯历史变成一次连续手势：滚轮、触摸或键盘到达顶部即加载、锚定并落定下一页，无需点击，内容也不跳动。`chat.loadOlder` 文案键、按钮及其 CSS 被移除；在途胶囊保留加载反馈。单元测试覆盖触发、补满、守卫（在途、已耗尽）、恢复到顶链式与链式 prepend；`chat-scroll-contract.e2e.ts` 的翻页步骤改写为围绕到达手势（先在触发区上方采样锚点，再到达），`stats-paged-history.e2e.ts` 滚动到顶来翻页，`complex-history.perf.ts` 按到达驱动的翻页逐页计时。轨迹时间线保留自己的 Load-earlier-history 按钮——不同组件，不在范围内。

页面落定后读者的位置是触发时位置加上 prepend 高度的下移量；连续翻页需要一次次到达顶部，每页一次网络往返，这正是预期的节奏。
